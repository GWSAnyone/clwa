## moduleAgnosticVerdict

ALMOST MODULE-AGNOSTIC, BUT NOT FULLY. The engine is approximately 95% module-agnostic. 40+ registries cover the extension surface comprehensively — event types, source flags, step handlers, discovery handlers, day-advance handlers, tick phase handlers, consequence post-handlers, affordances, target finders, requirement checkers, and more are all cleanly delegated. HOWEVER, the engine contains several concrete leaks of crime-justice module vocabulary that break INV-14 in practice. The critical test: "If I add an Economy module with FRAUD/SMUGGLING — does the engine handle it without code changes?" MOSTLY YES for events/affordances/CG/goals. But: (1) engine hardcodes 'rumor' as a belief source string in world.ts belief-transfer code — an Economy module with different gossip mechanics would need to reuse this exact string or the engine ignores its belief transfers; (2) engine pre-seeds default BELIEF_SOURCE_LABELS and SOURCE_TRANSFER_WEIGHTS for crime-specific source strings like 'body_discovery', 'deduction', 'evidence' — an Economy module would have to override these or accept irrelevant defaults; (3) engine agent.ts builds prompts with crime-specific prose ("You are wanted for a crime", "the guard coming for you", "ACTIVE DUTY: investigating the [crime] of [victim]") that only make sense in a crime context; (4) secret-directives.ts in engine contains inline crime-specific behavioral prose; (5) concepts like CrimeScene, processKill, markCrimeScene are engine-level primitives with crime-specific naming and semantics. The ARCHITECTURE is sound — registries genuinely work, the separation pattern is proven. But the implementation has accumulated crime-justice module knowledge in the engine layer.

## notes

OVERALL ASSESSMENT: The CLWA engine architecture is WELL-DESIGNED and MOSTLY delivers on its promise. The 53 registries represent genuine architectural commitment to module-agnosticism. For a new Economy module: (1) event types, CG rules, affordances, step handlers, target finders would all work through existing registries with zero engine changes — this is the STRONG 90%. (2) BUT: you would need engine changes for new AgentProfile capability flags (e.g. 'isMerchant'), new AffordanceRequirements fields (e.g. 'hasTradeGoods'), and you'd get crime-specific prompt prose leaking into NPC behavior. (3) The 'rumor' source hardcoded in world.ts is the most actionable bug — should be BELIEF_SOURCE.GOSSIP or a configurable string. (4) The pre-seeded defaults in event-registry.ts (BELIEF_SOURCE_LABELS, SOURCE_TRANSFER_WEIGHTS) are a minor smell — modules already override them, so they're technically dead defaults, but they document engine assumptions about what sources exist. (5) The biggest structural issue is AffordanceRequirements and AgentProfile — these are rigid engine types that must change for each new module domain. The fix: convert capability flags to a generic Map<string, boolean> and AffordanceRequirements to use only the REQUIREMENT_CHECKERS registry (which already exists and works!). The AffordanceRequirements type fields like 'isCriminal' should be removed from the type definition — they're already checked via registry. (6) The prompt prose in agent.ts/secret-directives.ts could be moved to a registry of 'directive builders' — secret-directives.ts already has this pattern (getSecretDirectiveBuilders), but the engine's own sections 1-3 should also be delegated to module-registered builders instead of being inline. PRIORITY: (A) Fix 'rumor' hardcode -> BELIEF_SOURCE constant or registry, (B) Make AffordanceRequirements fully registry-based (remove hardcoded field names), (C) Move prompt prose from agent.ts/secret-directives.ts inline sections to registered builders, (D) Clean up pre-seeded defaults. All are achievable without restructuring. The fundamental architecture pattern is CORRECT and PROVEN.
