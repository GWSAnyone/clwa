# probe-peaceful-trading-village-economy-sim-pro

> Per-agent structured output (final answer). Raw `.jsonl` transcript alongside.

## genre

Peaceful Trading Village — economy sim (produce/buy/sell/price/undercut/rivalry), zero crime/justice

## moduleOnlyNeeds

- EVENT TYPES (TRADE_COMPLETED, PRICE_CHANGED, GOODS_PRODUCED, UNDERCUT): registerEventCategory + registerEventLabels + registerEventTypeFlags. Engine's EventType is just `string` (cg-types.ts:3); no union to extend.
- AFFORDANCES (haggle, produce, undercut, set_price, open_stall): push to AFFORDANCE_REGISTRY with OCEAN+H weights. The scoring engine (computeUtility in al.ts) is genre-agnostic — profit-greed maps cleanly to existing trait weights (low-A/low-H undercut, high-C produce) + moodWeight + relationshipWeight (business rivalry = negative sentiment). NO engine change for motivation.
- ACTION VERBS (sell, buy, haggle, undercut): registerActionVerbs() maps LLM verbs → affordance IDs. Volition schema enum auto-includes them (volition.ts:getVolitionSchema).
- STEP HANDLERS (produce_goods, execute_trade, change_price): registerStepHandler — engine runs them via the generic `default` case in goals.ts executeStep. Handlers mutate state, observe, adjust relationships, emit events exactly like steal_from/arrest do.
- CONSEQUENCE RULES (undercut → rival resentment, price spike → cascading distrust, monopoly → community anger): push ConsequenceRule[] into the CG rules array. cg-engine.ts is fully generic — conditions use trait/relationship/belief/has_capability/eq/gt/lt ops, targetMode witnesses/location/affected/all. Economic ripple = same machinery as crime cascade.
- BELIEFS about economic events (X overcharges, Y undercuts, Z hoards): beliefs.ts BeliefManager is event-type-agnostic — belief.eventType is a free string. registerBeliefCreator/registerMemoryTextBuilder/registerSourceDecayRates produce economic beliefs.
- TOPIC SOURCES (NPCs gossip about prices/deals): TOPIC_SOURCE_REGISTRY.push + registerTopicGroupMapping — same as social/index.ts.
- CAPABILITY FLAGS for roles (merchant/producer/guild-master): reuse the AgentProfile flag pattern; CG has_capability + REQUIREMENT_CHECKERS read arbitrary profile fields generically (cg-engine.ts:evaluateFilter reads profile[capFlag]).
- MOOD/SENTIMENT consequences of trade outcomes: registerEventMoodShifts, registerConsequencePostHandler, registerGoalMoodBoost — profit boosts mood, getting undercut drops it. Reuses SPEC-mood-modifiers.

## forcedEngineChanges

- **change**: Real economic STATE: wealth balance + inventory quantities + goods ownership on the agent. AgentState (agent-types.ts) has alive/status/location/mood/beliefs/relationships but NO numeric wealth, NO mutable inventory, NO ownership ledger. AgentProfile.shop is a STATIC ShopItem[] (id/name/price/description) with no quantity and no buy-side balance mutation.; **reason**: A trading-village core loop (accumulate wealth, deplete/replenish stock, transfer ownership on a sale) needs persistent mutable numeric state that survives save/load. A module can stash ad-hoc numbers in goal.data, but that is transient and not serialized as agent state; there is no engine-owned, persisted wealth/inventory field, no save.json schema slot, and no engine helper to atomically transfer value between two agents. This is genuinely a capability the engine lacks for ALL economic/RPG genres.; **classification**: new-universal-capability
- **change**: Generalize the crime-specific AffordanceRequirement fields. al.ts AffordanceRequirement hardcodes isCriminal, isWanted, hasDetainedNpc, hasCrimeBelief, beliefConfidence, hasWitnessBelief, notPerpetrator, canSentence, hasSuspicionBelief, deductionBelowThreshold as named boolean fields on the ENGINE interface; checkRequirements/validatePlayerAction iterate REQUIREMENT_CHECKERS by these keys.; **reason**: A trade module needs requirement gates like hasStock, canAfford, ownsShop. The registry (REQUIREMENT_CHECKERS) is open, so a module CAN register new checker keys — but the typed AffordanceRequirement interface lists crime concepts by name, so a trade requirement is either untyped (cast) or forces adding economic fields to the engine type. Strictly a module CAN work via the generic record cast, but the engine TYPE leaks crime vocabulary; cleanly supporting trade requirements wants these moved to a generic shape.; **classification**: crime-assumption-leak
- **change**: world.ts crime orchestration: markCrimeScene(), crimeScenes Map<string,CrimeScene[]>, onMurder callback, bodyDiscoveries set + body-discovery co-location loop, and the engine types CrimeScene/ExaminationPoint/CrimeSceneJSON (world-types.ts), TickResult.murder, TickResult.crimeScene.; **reason**: None of this fires in a no-crime village (no death events, no scene types registered), so it is inert rather than blocking. But it is dead crime-domain weight living in the engine: the engine OWNS the concept of a 'crime scene' and 'murder/body discovery' as first-class types and tick logic, instead of these being a module-registered 'world-marker' abstraction. A politics/economy world that wanted its OWN persistent location-marker concept (e.g. a 'market stall' or 'contested territory') would find the generic version absent — only the crime-named one exists.; **classification**: crime-assumption-leak
- **change**: il.ts engine-resident TradeIntent: TradeIntent interface, tradeIntent JSON-schema branch, the hardcoded prompt line '"trade" = player wants to buy, sell, browse goods, or ask about prices', trade-detection correction logic, and EmotionalPressure.type union ('threat'|'bribe'|'flattery'|'guilt'|'intimidation').; **reason**: Interesting double-edge: the engine ALREADY contains primitive trade plumbing (player→NPC shop browse), so a trading village partly benefits for free. But it is a leak: trade concepts are baked into the engine Intent Layer rather than module-registered the way speech acts / pressure types / claim sources are. The EmotionalPressure type union is hardcoded (the runtime correctly uses getRegisteredPressureTypes(), but the TS type is fixed), so a module adding an economic pressure like 'lowball'/'price-gouge' gets runtime support yet a stale engine type. Module works around it, but extending trade semantics (negotiation, counteroffers, contracts) means editing engine il.ts.; **classification**: crime-assumption-leak
- **change**: GoalActionResult.crimeEvent field (goals.ts) and TickResult.murder/crimeScene (world-types.ts) in the engine's public result shapes.; **reason**: A trade step handler that completes a sale has no 'crimeEvent' to populate; it would reuse the generic event path, but the engine result contract names a crime-specific channel. Purely a naming leak — does not block a module (the field is optional) — but proves crime vocabulary is in the engine's universal output types.; **classification**: crime-assumption-leak

## verdict

occasional-engine: the behavioral core (CG cascade, volition/PM scoring, goals/steps, beliefs, mood) is genuinely universal and a trading village is ~85% module-only — but it forces exactly ONE legitimate new-universal-capability (persistent mutable wealth/inventory/ownership state on the agent), and it surfaces several crime-assumption leaks (typed AffordanceRequirement fields, world.ts crime-scene orchestration, il.ts TradeIntent, GoalActionResult.crimeEvent) that a clean economy module would want cleaned up rather than worked-around.

## confidence

high — claims are grounded in direct reads of al.ts, volition.ts, cg-engine.ts, cg-types.ts, goals.ts, agent-types.ts, world-types.ts, world.ts, il.ts, event-registry.ts and the crime-justice module (index/affordances/step-handlers). The one inference not 100% verified: that no wealth/inventory state exists anywhere — confirmed by a negative grep across packages (only comments/false-positives), but I did not read server.ts trade endpoint fully.

## notes

Skeptical bottom line: the claim 'new game = new module, zero engine changes' is MOSTLY true for behavior/motivation/consequences but FALSE for state. The PM/volition pipeline cleanly supports profit/greed as a non-crime motive with no engine change — that part of the promise holds (computeUtility in al.ts is domain-agnostic; greed = low-H/low-A weights + relationshipWeight on rival sentiment). The CG engine generalizing to economic ripple effects also holds — cg-engine.ts has zero crime knowledge, everything is via getBeliefCreator/getMemoryTextBuilder registries. The genuine wall is STATE: there is no engine-owned, persisted, mutable wealth/inventory/ownership model and no atomic value-transfer helper — agent-types.ts AgentState lacks it and AgentProfile.shop is a static read-only price list. That is a real missing universal capability (every economy/RPG/4X world needs it), not a crime leak. Separately, the audit exposes that the engine is not crime-PURE either: it already leaks a primitive TradeIntent into il.ts — so the engine is milestone-coupled to BOTH crime and a half-built economy, which weakens INV-14's 'zero module-specific strings' claim. Recommendation if pursuing this genre: (1) add a generic numeric/resource state slab to AgentState + save schema (one-time universal investment), (2) refactor crime-named engine surfaces (AffordanceRequirement fields, CrimeScene→generic WorldMarker, TradeIntent→module-registered intent kind, crimeEvent→genericEvent) into neutral abstractions. After that one engine investment, subsequent economy content is genuinely module-only.
