# map-knowledge-agency-subsystems-beliefs-il-g

> Per-agent structured output (final answer). Raw `.jsonl` transcript alongside.

## area

Knowledge & Agency subsystems (beliefs, IL, goals, perception, relationships, memory, affordances)

## universal

- beliefs.ts:Belief is fully event-typed and genre-agnostic: {eventType:string, subject/object/location:string|null, confidence, source:string, sourceNpcId, gameDay}. It is a generic propositional-attitude store ('who did what to whom, how sure, how learned'). Nothing crime-specific in the shape — FRAUD/SMUGGLING/TRADE_DISPUTE beliefs would store identically. Decay, reinforce/merge, query-by-(eventType|subject|object), confidence-weighted summaries are all driven by registry lookups (getSourceDecayRate/getEventTypeDecayRate/getEventLabel), not literals.
- beliefs.ts:BeliefSource is `type BeliefSource = string` with all labels/weights/decay/category in event-registry.ts registries (registerBeliefSourceLabels, registerSourceTransferWeights, registerSourceDecayRates, registerSourceCategory). A new genre adds sources (e.g. 'ledger_audit','market_report') with no engine edit.
- event-registry.ts: This is the genuine genre-agnostic backbone — ~40 registries with register*/get* pairs and flag-based dispatch (EventTypeFlags.transferable/informationOnly/subjectReacts/decayRate; SourceFlags.perpetrator/firsthand/concealment). Engine logic checks FLAGS not category strings (isTransferable/subjectReacts/isDeathEvent), so the propagation/decay/reaction machinery is content-neutral. cg-types.ts:EventType and WorldEvent are `string`-typed with a free `payload: Record<string,unknown>` — any event shape passes through the consequence graph.
- goals.ts: The step VM is well-factored. Built-in primitives (move_to, interact, interact_present, announce, wait) are universal physical/social verbs; everything else dispatches to getStepHandler(action) (ModuleStep). GoalManager (priority sort, preemption, watchdog sweepStuckGoals, target-of-goal queries, type-based completion) is pure scheduling logic with zero crime content. NpcGoal.type/data are free strings/bags. transferBeliefs() gates on isTransferable() (registry), not event names.
- il.ts: SpeechAct is `string`; speech acts, claim sources, pressure types, question topics, trade verbs, action verbs are ALL registry-driven enums injected into the LLM JSON schema (buildILSchema reads getRegisteredSpeechActs/getRegisteredClaimSources/getRegisteredPressureTypes/getRegisteredQuestionTopics/getILTradeVerbs). The IL->engine effect pipeline (claims->beliefs, questions->belief gather, requestedAction->goalCreator via getAffordanceIdsForVerb, pressure->mood/relationship + getPressureHandler, speechActEffects) is a generic 'player utterance -> structured meaning -> engine primitive' bridge. emotionalPressure aside, the routing is genre-neutral.
- al.ts:AffordanceDefinition is a strong genre-agnostic utility model: OCEAN+H personality weights, non-linear mood/sentiment curves, beliefModifiers (boost score by confidence in matching beliefs), trustWeight, declarative stepTemplates with {var:fallback} interpolation, registry-based target finders (TARGET_FINDERS/REACTIVE_TARGET_FINDERS) and requirement checkers (REQUIREMENT_CHECKERS keyed by field name). computeUtility() is pure math over personality/mood/relationship/belief/trust — no crime knowledge. Any genre's actions plug in as data.
- relationships.ts:RelationshipGraph (sentiment -1..1, trust 0..1, onChange->WS broadcast, bilateral adjust) is universal social state, reused by IL, conversation, accusation, volition. memory.ts:VectorMemory (embeddings, composite recall relevance/importance/freshness, decay, eviction, player-scoped WORLD_MEMORY_OWNER for multiplayer) is fully content-agnostic episodic memory. agent.observe() is a generic 'perceive text + maybe reflect' sink.
- Bilateral design holds across these subsystems: Player is an Agent with isPlayer; beliefs, relationships, perception, memory all work identically for player and NPC (INV-16 guards present in loops).

## lockedOrLimiting

- al.ts:AffordanceRequirement (lines 11-49) — the interface hardcodes crime-justice domain fields as named booleans: hasCrimeBelief, beliefConfidence, isCriminal, isWanted, hasDetainedNpc, hasWitnessBelief, notPerpetrator, hasSuspicionBelief, deductionBelowThreshold. The *checking* is delegated generically (checkRegistryRequirements iterates REQUIREMENT_CHECKERS by key, modules supply logic), so it is not a hard engine dependency — BUT the type surface is crime-flavored. An Economy module's affordance would either smuggle its predicate through a misnamed field or require adding new fields to this engine interface. This violates INV-14's spirit ('zero module-specific strings') at the type level even if runtime dispatch is clean. Also checkRegistryRequirements only forwards `beliefConfidence` as a param (line 294) — a hardcoded crime param name.
- al.ts:checkRequirements/checkRequirementsReactive (332-335, 365-368) — notGuard/isGuard are HARDCODED to `agent.profile.investigator`, and the engine wires isInvestigator/canSentence directly. 'Guard' == 'investigator capability' is baked in. A combat/economy module's role gates (e.g. 'isMerchant','isSoldier') have no first-class path and must reuse the generic capability-flag pattern, but the existing named checks are crime-role-shaped. al.ts:checkPostTargetRequirements (302-320) hardcodes noGuardNearby->detersCrime, maxWitnesses, sentimentBelow — witness/guard concepts in engine.
- agent-types.ts:AgentProfile (82-111) — capability flags investigator/detersCrime/canSentence and the `shop: ShopItem[]` field are crime-justice/trade-specific fields living in the ENGINE profile type. shop/ShopItem (113-118: id/name/price/description) is the only economic vocabulary in the engine and it is a dead-end: it is a static display list for trade dialogue, with NO transactional state behind it (no buyer balance, no inventory transfer). This is module content leaked into an engine type.
- il.ts:EmotionalPressure (147-150) — `type: 'threat'|'bribe'|'flattery'|'guilt'|'intimidation'` is a HARDCODED union literal, contradicting the otherwise registry-driven pressure types (getRegisteredPressureTypes). This is a concrete locked enum on the engine IL output type. (Runtime validation uses the registry; the TS type is stale/crime-social-specific.)
- relationships.ts:RelationType (1-8) is a CLOSED union (friend|rival|family|acquaintance|romantic|mentor|colleague) with hardcoded DEFAULT_TRUST/DEFAULT_SENTIMENT/getGriefPenalty tables keyed by those literals. No political/factional relations (ally/enemy-faction/vassal/citizen) and no way to add relation types without editing the engine. getGriefPenalty bakes in a death-grief model. This is a real engine-level constraint for politics/combat.
- PERCEPTION IS BINARY CO-LOCATION, NOT SPATIAL (world.ts ~1071-1073, goals.ts announce 622-644): witnessing = `a.state.alive && a.state.location === crimeData.location`. There is no line-of-sight, range, sensory radius, stealth/detection, or intra-location position for perception. Movement is graph-hop between named LocationDef nodes (world-types.ts:LocationDef = id/name/connections/isPublic). Combat (spatial threat, range, cover) and stealth-economy (smuggling visibility) have no substrate — 'present at the same node' is the only spatial primitive.
- There is NO numeric/resource state model anywhere in the engine. agent-types.ts:AgentState has alive/status/location/mood/baseMood/moodModifiers/currentDay/knownFacts/beliefs/relationships — no health/HP, no stamina, no money/balance, no inventory, no owned items, no faction membership, no reputation/standing scalar. 'Theft' (step-handlers.ts:216-221) emits a GOODS_STOLEN event + observe() but mutates NO inventory because none exists. The whole world is symbolic/social; quantitative simulation state is absent.
- goals.ts:loadFromJSON (352) hardcodes BUILT_IN_ACTIONS set; fine, but combined with the fact that all consequence/economy effects must round-trip through events+beliefs (no ledger), there is no transactional integrity layer — an economy module would have to invent its own state store outside the engine's persisted AgentState.

## gaps

- ECONOMY needs: (1) a numeric resource/currency balance on Agent (engine-level, persisted) — none exists; (2) a real Inventory/ownership model (item instances with owner refs, quantities) — only a static AgentProfile.shop display list exists, no transfer; (3) value/price beliefs (an Agent's belief about an item's worth or another's wealth) — Belief only models event propositions (who-did-what), not valuations or quantitative facts; (4) a transactional affordance result that atomically moves money+goods — step handlers only observe()+emit events, no state mutation primitive; (5) economic relationship types (creditor/debtor/employer) and trust-as-creditworthiness.
- COMBAT needs: (1) health/HP/wound state on AgentState (only a boolean `alive` + DEATH_EVENTS exist — death is instantaneous via event, no damage accumulation); (2) damage/attack resolution primitives (current 'kill' is a binary affordance->event, no hit/miss/damage math); (3) spatial threat & range — perception/positioning is node-level co-location only, no line-of-sight, distance, cover, or fleeing-by-distance; (4) equipment/weapon state (no inventory to hold a weapon); (5) combat-stance relationships (ally/enemy) — RelationType union has no martial relations; (6) initiative/turn or real-time tick resolution for exchanges — goal VM is sequential one-step-per-tick, not a combat loop.
- POLITICS needs: (1) faction/group entities and membership on Agent (no group abstraction exists — only per-pair Relationship edges); (2) influence/standing/reputation scalars per (agent,faction) — no numeric standing anywhere; (3) factional relationship types and faction-vs-faction state (RelationType is interpersonal-only, closed union); (4) collective beliefs / shared faction knowledge (Belief + memory are per-agent; WORLD_MEMORY_OWNER exists for shared episodic memory but there's no faction-scoped belief aggregation); (5) authority/legitimacy as data (canSentence is a boolean flag, not a graded political-power model); (6) coalition/voting/decree mechanics over the goal/event system.
- DEEPER SIM (cross-genre): (1) a generic typed numeric-attribute system on Agent (the recurring miss — health, gold, stamina, standing are all the same shape: a named decaying/clamped scalar with modifiers; mood already has exactly this via MoodModifier — generalize it); (2) an entity/item layer (currently only Agents + Locations + CrimeScenes exist as world entities — no generic 'object/item' with owner/location/state); (3) richer perception (range, senses, detectability) as a registry-driven layer; (4) AffordanceRequirement/AffordanceTarget gating on arbitrary numeric attributes (cost>=price, hp>0, standing>=threshold) — current requirement model is boolean/threshold over mood/sentiment/belief only.

## extensionPoints

- event-registry.ts (~40 registries) is the primary extension surface: registerEventTypeFlags(Batch), registerSourceFlags, registerEventCategory, registerEventLabels, registerEventHandler, registerActionVerbs, registerStepHandler, registerDiscoveryHandler, registerDayAdvanceHandler, registerTickPhaseHandler, registerConsequencePostHandler, registerPressureTypes/Handler, registerSpeechActs, registerClaimSources, registerQuestionTopics, registerILTradeVerbs, registerBeliefSourceLabels/TransferWeights/DecayRates/Category, registerEventMoodShifts, registerGoalMoodBoost, registerCrimeSceneTemplate, registerEventSceneTypes, registerSecretDirectiveBuilder, etc. A new genre fills these at startup; engine never imports the module (modules->engine only, per CLAUDE.md).
- al.ts agency extension: push AffordanceDefinition into AFFORDANCE_REGISTRY; register TARGET_FINDERS/REACTIVE_TARGET_FINDERS (keyed by affordance id or targetFinder); register REQUIREMENT_CHECKERS (keyed by requirement field name — this is HOW a new genre adds gating predicates without engine edits, though new fields still want a type on AffordanceRequirement); registerBlockingGoalTypes. computeUtility consumes weights/moodWeight/relationshipWeight/beliefModifiers/trustWeight/minimumScore declaratively.
- goals.ts step extension: register custom step actions via registerStepHandler(action, fn); the StepExecutionContext hands handlers agents/locations/runInteraction/onCrimeEvent/crimeScenes/evidenceLayer/goalManager/addMoodModifier. Goals are built declaratively from AffordanceDefinition.stepTemplates with $target/$home/$extra.KEY/{var:fallback} interpolation, so most new actions need only a handler + templates.
- il.ts speech extension: register speech acts (registerSpeechActs with benign/trade/accusation flags), claim sources, pressure types+handlers (registerPressureHandler), question topics, trade/action verbs; configure effects via ILConfig.pressureEffects/speechActEffects/importanceValues. registerAccusationResponseHandler is a module hook for authority responses. applyDialogueMeaning then routes generically. Adding e.g. a 'negotiate'/'offer'/'declare_war' speech act is data + a handler.
- beliefs/memory extension: BeliefManager is constructed per-agent in AgentState.beliefs; new event types just need registerEventLabels + flags. VectorMemory accepts options (collection per agent, vectorSize, maxCapacity) and is content-neutral. Capability-flag pattern on AgentProfile (investigator/detersCrime/canSentence) is the intended way to add role behavior — a new genre would add flags (but those flags currently live in the engine AgentProfile type, so adding them is an engine edit unless a generic capabilities bag is introduced).
